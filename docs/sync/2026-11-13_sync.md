## Expériences et résultats

### 1. Diagnostic : pourquoi le k oracle est pire que l'eigengap
- **Ce qui change** : seulement k (eigengap vs nombre réel de locuteurs n_ref). **Fixe** : embeddings, graphe
  (p_neighbors 0.1, max_speakers 10), KMeans seed 42, post-traitement.
- **Fichiers** : dev sample 90 (`samples/dev/sample90_seed130.rttm`). Test non consulté.
- **Résultats** (DER moderne, eigengap → k oracle) :

| VAD | eigengap | k oracle |
|---|---|---|

| best_vad alldev | 29,71 % | 33,92 % |
| best_vad devtrain | 30,14 % | 34,23 % |
| VAD oracle | 28,67 % | 33,06 % |

- VAD oracle, détail : DER forgiving 25,99 → 30,28 % ; JER 61,13 → 53,46 % ; confusion 21,77 → 26,16 % ; FA (0,03 %) et

### 2. Amélioration n°2 candidate : NME-SC
- **Principe** : pour chaque fichier, on teste 30 valeurs du nombre de voisins p gardés par window dans le graphe (de 5 à
  25 % des windows) et on garde celle qui minimise r(p) = p / g_p, où g_p = plus grand eigengap / plus grande valeur propre.
  k = position de l'eigengap maximal pour ce p. Référence : Park et al., 2019 (« Normalized Maximum Eigengap »).
- **Ce qui change** : le choix de p (et, pour la 3e variante, aussi le Laplacien). **Fixe** : VAD `best_vad(train="devtrain")`,
  MFCC, embeddings (calculés une seule fois par fichier pour les 3 variantes), max_speakers 20, min_neighbors 5, seed 42,
  post-traitement.
- **Fichiers** : dev sample 90. Test non consulté. Collar 0, UEM = durée du wav, micro.

| Variante | DER moderne | DER forgiving | JER | FA | missed | confusion | k exact | k sous-estimé | k surestimé |
|---|---|---|---|---|---|---|---|---|---|
| p fixe 0.02 (baseline du 13/11) | 29,09 % | 26,21 % | 52,91 % | 1,62 % | 6,32 % | 21,15 % | 44,44 % | 34,44 % | 21,11 % |
| NME-SC, Laplacien normalisé | 27,39 % | 24,48 % | 54,85 % | 1,62 % | 6,32 % | 19,46 % | 43,33 % | 46,67 % | 10,00 % |
| NME-SC, Laplacien non normalisé | 26,04 % | 23,11 % | 55,27 % | 1,62 % | 6,32 % | 18,10 % | 41,11 % | 51,11 % | 7,78 % |

- VAD detection error : 3,13 % (identique pour les 3). RTF ≈ 0,01 pour les 3 (coût de NME-SC négligeable).
- Sources : `results/nme_sc/agregats_sample90_seed130.csv`, CSV par fichier et RTTM dans `results/nme_sc/`.

## Observé / interprétation / hypothèses

### Observé
- k oracle : la hausse de confusion vient des 50 fichiers où l'eigengap sous-estime k (+4,92 pts) ; le locuteur dominant y
  est coupé dans 45 fichiers (2,96 clusters en moyenne au lieu de 1,28). 172 locuteurs sur 379 ont moins de windows que le
  nombre de voisins gardés (p = 10 % des windows).
- Avec les mêmes embeddings, le meilleur k par fichier (choisi avec la référence) donnerait 22,77 % de DER contre 30,83 %
  pour l'eigengap (79 fichiers, VAD oracle).
- NME-SC : sur 90 fichiers, 20 (normalisé) / 22 (non normalisé) s'améliorent de plus de 0,5 pt, 22 / 22 se dégradent de
  plus de 0,5 pt. Plus fort gain : hiyis (2 locuteurs, k 18 → 2, DER 84,0 → 1,5 %). Plus fortes pertes : bauzd
  (k 3 → 5, DER 19,8 → 61,5 %), lfzib (9 locuteurs, k 9 → 2, DER 27,4 → 54,5 %).
- Le « p fixe 0.02 » vaut en réalité 5 voisins (minimum imposé) sur 57 fichiers sur 90.

### Interprétation
- Le DER pondère par le temps de parole, le JER pondère chaque locuteur à égalité. Oublier un petit locuteur coûte peu en
  DER mais beaucoup en JER ; couper le dominant coûte beaucoup en DER. Les deux métriques regardent le même compromis avec
  des poids différents, ce qui explique les sens opposés (k oracle comme NME-SC).
- NME-SC supprime les surestimations catastrophiques dues à un graphe trop creux (5 voisins), au prix de plus de
  sous-estimations : meilleur DER, JER moins bon.

### Hypothèses (non vérifiées)
- Le gain de NME-SC repose sur quelques fichiers : sa stabilité n'est pas établie (autres seeds de KMeans, autres fichiers
  dev hors entraînement de la VAD).
- Une partie du gain de NME-SC pourrait venir de `max_speakers = 20`, qui laisse le p fixe surestimer fortement k.
- La confusion du k oracle augmente surtout sur les trames couvertes par des windows de labels différents (592 s → 2 247 s) :
  probablement un symptôme du découpage du dominant, peut-être aussi un effet des windows de 2 s et du vote (à vérifier
  dans `figures_exploration/p08_overlap_frontieres/`).

## Problèmes, écarts au protocole
- **Fuite possible** : `baseline.py` et `baseline_oracle.py` utilisent `best_vad(train="alldev")`, entraînée sur les
  216 fichiers dev, dont les 90 du sample de réglage. Tout chiffre de la baseline sur le dev sample 90 avec cette VAD est
  optimiste. Les expériences du diagnostic et de NME-SC utilisent `train="devtrain"` (sans fuite).
- **Comparaisons non alignées** : `baseline_oracle.py` n'utilise pas les mêmes paramètres de clustering que `baseline.py`
  (0.1 / 10 contre 0.02 / 20). Les runs oracle et baseline ne sont donc pas comparables entre eux.
